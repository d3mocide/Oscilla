| **D-10** | SX1262 TCXO startup delay & voltage encoding | ✅ Decided | **Voltage settled, delay is a bench-verified starting point, not a guess.** From the official SX1262 datasheet (`SetDIO3AsTCXOCtrl`, opcode `0x97`, §13.3.6): `tcxoVoltage` is an enum, not a raw value — **use `0x02` = 1.8 V**, which satisfies both the Wio module's documented 1.7–3.3 V TCXO range and the chip's hard rule `VDDop > VTCXO + 200 mV` (3.3 V supply − 1.8 V leaves a 1.5 V margin). `delay(23:0)` is exact: `delay × 15.625 µs`. The specific startup time is genuinely TCXO-component-specific — Semtech's datasheet says so explicitly, and Seeed's Wio-SX1262 datasheet never names the TCXO part, so no source states an exact number. Resolution: **start at `delay = 640` (10 ms)** — conservative for any common 32 MHz TCXO, and the chip self-reports if it's wrong (`XOSC_START_ERR` flag, cleared via `ClearDeviceErrors`, no damage from a too-short delay, just a flag). Enter `STDBY_XOSC` before RX to pay this cost once rather than per-burst (datasheet's own recommended technique). Bench bring-up confirms no `XOSC_START_ERR` at 10 ms; tightening it further is optional, not required. | P3 |

| **D-18** | 802.15.4 leaves Wi-Fi/BLE dead until a real reboot | ✅ Decided (upstream defect, workaround shipped) | **Not an Oscilla bug — a documented, unfixed ESP32-C5 coexistence defect with no app-level fix, worked around by a guarded automatic probe reboot.** Stopping the 802.15.4 engine, even a single clean start-then-cancel with zero inbound traffic, silently zeroed out subsequent Wi-Fi Scan/Packet Monitor/BLE Scan results — commands acked normally, no `[ERR]`, just empty. Ruled out in order, each with hardware evidence: (1) a suspected `zig_task`/`zig_teardown()` race calling `esp_ieee802154_disable()` concurrently with a live `receive()`/`set_channel()` call — fixed (bounded wait for a task-idle flag, same idiom as `ocp_frame.c`'s `FRAME_LOCK_WAIT_MS`), verified not sufficient alone; (2) missing the same Wi-Fi-driver stop/start bounce `wifi_spectrum.c` needs after promiscuous mode (`wifi_recon_restore_shared_phy()`, renamed from `_after_promiscuous`) — added, verified **not sufficient either**, a clean single 802.15.4 start→confirmed-active→stop→confirmed-inactive cycle still zeroed a real 120-AP environment. Traced into vendored ESP-IDF (`components/esp_phy/src/phy_init.c`): `esp_phy_disable()` fully closes the shared RF (`phy_close_rf()`) unless another modem's flag is concurrently held, and `esp_phy_enable()`'s recalibration path only runs once — `s_is_phy_calibrated` never resets except at boot, with no public API to force it. ## Notes

- **D-8 restores the v0.1 stance.** After briefly designing a compile+runtime transmit gate (to keep TX reachable long-term), we reverted to plain receive-only: no TX verbs compiled, so no reachable transmit path. This is a genuine structural guarantee again (with the honest caveat that the SX1262 hardware is TX-capable), and it removes region/duty (D-9) from scope entirely. The long-term option to add TX is preserved by architecture, not by shipped code (D-13).
- **Blocking decisions** (⛔) are surfaced in ROADMAP at their phase entry gates. None currently blocking (D-12 resolved 2026-09-12, D-10 resolved 2026-09-13).
